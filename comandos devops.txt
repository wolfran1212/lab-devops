═══════════════════════════════════════════════════════════════════════
  PASO 1 — CREAR DASHBOARD
═══════════════════════════════════════════════════════════════════════

gcloud monitoring dashboards create \
  --config-from-file=dashboard.json \
  --project=cicdtraining-498421

  ✎ NOTA: Crea el dashboard con 4 widgets en Cloud Monitoring:
           error rate · latencia p95 · disponibilidad · instancias activas.
           Verlo en: console.cloud.google.com → Monitoring → Dashboards

═══════════════════════════════════════════════════════════════════════
  PASO 2 — CREAR LAS 3 POLÍTICAS DE ALERTA
═══════════════════════════════════════════════════════════════════════

  ── Alerta 1: Error Rate > 0.5% por 2 minutos ──
gcloud monitoring policies create \
  --policy-from-file=alert-errors.json \
  --project=cicdtraining-498421

  ✎ NOTA: ID resultante → 11182487088173636770
           Condición: tasa de errores HTTP supera 0.5% sostenido 2 min.
           SLO asociado: Availability ≥ 99.5%

  ── Alerta 2: Latencia p95 > 500ms por 2 minutos ──
gcloud monitoring policies create \
  --policy-from-file=alert-latency.json \
  --project=cicdtraining-498421

  ✎ NOTA: ID resultante → 6022321838366663113
           Condición: percentil 95 de latencia supera 500ms sostenido 2 min.
           SLO asociado: Latencia p95 < 500ms

  ── Alerta 3: Availability < 99.5% por 5 minutos ──
gcloud monitoring policies create \
  --policy-from-file=alert-availability.json \
  --project=cicdtraining-498421

  ✎ NOTA: ID resultante → 6022321838366666603
           Condición: porcentaje de respuestas 2xx cae bajo 99.5% por 5 min.
           SLO asociado: Error rate ≤ 0.5%

  ── Verificar las 3 alertas creadas ──
gcloud monitoring policies list \
  --project=cicdtraining-498421

  ✎ NOTA: Confirmar que las 3 aparecen con enabled: true
           Si alguna falta, repetir el comando create correspondiente.

═══════════════════════════════════════════════════════════════════════
  PASO 5 — DISPARAR LAS ALERTAS (ROMPER LOS SLOs)
═══════════════════════════════════════════════════════════════════════

  ── Opción A: Desde CMD (dos ventanas simultáneas) ──

  Ventana 1 — forzar errores 500:
    for /L %i in (1,1,500) do curl -s "https://mi-app-622078306811.us-central1.run.app/api/work?ms=200&fail=true" > nul

  Ventana 2 — forzar latencia alta:
    for /L %i in (1,1,200) do curl -s "https://mi-app-622078306811.us-central1.run.app/api/work?ms=800" > nul

  ── Opción B: Desde consola del navegador (DevTools → Console) ──

  // Errores masivos simultáneos
  for(let i=0; i<50; i++){
    fetch('https://mi-app-622078306811.us-central1.run.app/api/work?ms=200&fail=true')
      .then(r => console.log('status:', r.status))
  }

  // Latencia alta simultánea
  for(let i=0; i<20; i++){
    fetch('https://mi-app-622078306811.us-central1.run.app/api/work?ms=900')
      .then(r => console.log('ok:', r.status))
  }

  ── Opción C: k6 (carga sostenida completa) ──
    k6 run load-test.js

  ✎ NOTA: Mantener la carga AL MENOS 3 minutos continuos.
           Las alertas tienen ventana de evaluación de 2 min.
           El email llega 1-2 min después de que el incidente se registra.

  REFERENCIA RÁPIDA — SLOs DEFINIDOS

  SLI 1 — Disponibilidad

    Alerta ID  : 11182487088173636770

    SLO        : p95 < 500ms
    Alerta ID  : 6022321838366663113
